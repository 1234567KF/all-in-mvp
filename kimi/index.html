迭代模型

两种运行模式

全量模式用于全新项目，增量模式用于迭代追加功能

🆕

全量模式

全新项目

完整执行 Stage 1-4，全部模块一次到位。适用于第一次交付或重大重构。

  • PRD 从零编写，9 个强制章节全覆盖
  • 架构专家输出完整 spec + schema + api-contract
  • 所有模块按依赖图分批并行开发
📈

增量模式

迭代项目

每次迭代只跑涉及的 Stage，已锁定模块跳过。支持三种裁剪场景。

  • 新增独立模块：仅新模块走完整 Stage 2 流程
  • 修改现有模块：重走受影响部分的 ①→②→↺
  • Bug 修复：跳过 Stage 1-3，仅 Stage 4

决策原则

串行 vs 并行

明确什么时候必须串行，什么时候可以并行

⟳

什么时候必须串行？

  • PRD 未锁定前：所有 Stage2 Agent 必须等待
  • ↺ 拷问审查循环未通过前：Mock、TDD 必须等待
  • 模块间强依赖：如订单依赖用户
  • 接口契约变更：所有依赖 Agent 必须同步
  • 集成测试阶段：必须等前后端都完成
⇅

什么时候可以并行？

  • ③a Mock、③b-1 单模块测试、③b-2 场景测试：↺通过后并行
  • ③b-1 内部：最多 2 Agent 按模块平分
  • 无依赖模块的后端开发：用户管理 vs 类目管理
  • 前端 vs 后端：Mock 就绪后前端即可并行
  • Stage3 测试补充：事件驱动，与后端同步

质量保障

门禁与度量

每个阶段都有硬约束门禁，确保产出物质量

Stage 1 → Stage 2

  • PRD 文件 > 1KB
  • 9 个章节标题全存在
  • MECE 检查通过

Stage 2 → Stage 3

  • 所有产出物存在
  • MD5 与锁定时刻一致
  • YAML/JSON 语义可解析

Stage 3 → Stage 4

  • 所有模块目录存在 DONE 标记

  • L1-L5 测试全部通过

Stage 4 → 交付

  • 集成测试报告非空
  • 0 个 P0/P1 Bug
  • Mock-后端一致性验证

通信协议

Agent 间通信

文件驱动、单协调者模式，状态即文件

通信原则

  • 文件驱动：所有 Agent 通过读写约定目录下的文件协作
  • 单协调者：每个阶段协调角色唯一，工作 Agent 间不直接通信
  • 状态即文件：文件出现/更新 = 状态变更
  • 人类唯一入口：需人类决策的场景由协调者统一提交

文件状态约定

就绪待分配 模块目录不存在
已分配 目录存在，无 DONE 标记
已完成 存在 DONE 标记文件
异常/阻塞 存在 BLOCKED 标记 + 原因
推迟 存在 DEFER 标记 + reason.md
